# Инициатива агента: агент говорит первым

Архитектура для четырёх пробелов между постановкой (§1, §5) и кодом: агент
никогда не говорил первым, у этапов не было открывающей реплики, уход от
темы обрабатывается только промптом (осознанно, это так и осталось), а
первая фраза не была оптимизирована по задержке и ломала автоплей браузера.

**Статус: реализовано.** Ниже — описание того, как это устроено, а не план.
Что показал живой прогон и какие правки он породил — в разделе «Результаты
прогона» в конце.

## Проблема

1. **Агент никогда не говорит первым.** `Stage.agent_opening`
   (`packages/contracts/ath_contracts/scenario.py:27`) объявлен и заполнен
   в JSON сценариев, но никуда не отправляется. В
   `services/gateway/app/api/ws.py:55-56` прямо стоит TODO: *«отправить
   agent_opening текущего этапа сразу после подключения, чтобы инициативу
   держал агент — сейчас первый ход делает человек».* Клиент просто
   открывает сокет и ждёт.
2. **У перехода на новый этап тоже нет открывающей реплики.** `_run_turn`
   в `services/gateway/app/orchestrator/pipeline.py:126-131` вызывает
   `_speak()` (использует СТАРЫЙ этап) раньше, чем `_advance_stage()`
   (который может сменить этап). Цель нового этапа впервые появляется в
   системном промпте только на СЛЕДУЮЩЕЙ реплике пользователя — реактивно,
   никогда не как инициативная реплика агента.
3. **Уход от темы намеренно не обрабатывается в автомате.**
   `services/gateway/app/orchestrator/fsm.py:51-84`, `decide()`:
   `Classification.OFF_TOPIC` и `INCOMPLETE` попадают в одну и ту же ветку
   `STAY`, без различия. Докстринг: *«off_topic намеренно не наказывается
   отдельной веткой: возврат в русло — работа персонажа, а не автомата».*
   Это осознанный, уже существующий принцип кодовой базы — архитектура
   ниже его не нарушает.
4. **`completion_criteria` осознанно никогда не попадает в промпт
   персонажа** — только в промпт классификатора
   (`services/ai-service/app/character/prompts.py:79-98`). Любой новый
   текст промпта обязан сохранить это разделение: персонаж не должен знать
   критерий оценки, иначе не сможет случайно его не выдать.

Плюс два требования, которые реально следуют из самой фичи, а не просто
приятны в довесок (см. «Оптимизация задержки» и «Экран «Начать
тренировку»» ниже): раз момент открывающей реплики мы контролируем сами
(в отличие от реактивного ответа), его стоит оптимизировать кэшированием/
шаблонами; и раз агент теперь говорит раньше пользователя, автоплей звука
в браузере ломается без явного жеста пользователя.

## Единый механизм, две точки входа

Общий примитив: `TurnPipeline._speak` (pipeline.py:151) получает параметр
`is_opening: bool = False`. Но точка входа не может быть одна — два
структурно разных триггера:

- **Начало сессии**: `gen_id` ещё не заведён, нет события `UserMessage`, за
  которое можно зацепиться. Новый метод `TurnPipeline.open_session()`,
  вызывается из `services/gateway/app/api/ws.py` на месте TODO (строка
  55-56), под условием `if not session.turns:` (см. «Предпосылка:
  реконнект» ниже — у этого условия есть незакрытая зависимость). Метод сам
  делает `generations.bump()` + `generations.register()`, точно как
  `handle_user_message`, — barge-in и `is_stale()` работают без специальных
  случаев.
- **Переход на новый этап**: происходит ВНУТРИ уже выполняющейся задачи
  хода, сразу после того как `leave_stage()` отработает внутри
  `_advance_stage` (pipeline.py:~240). Использует ТОТ ЖЕ `gen_id` — это
  продолжение той же задачи, и barge-in в любом случае отменяет её целиком.

`_run_turn` (pipeline.py:126) становится:
```python
await self._speak(gen_id, user_text, recorder)
transition = await self._advance_stage(gen_id, user_text, recorder)  # теперь возвращает Transition
if transition.action is Action.NEXT_STAGE:
    await self._speak(gen_id, opening_directive_text, recorder, is_opening=True)
```
`_advance_stage` уже вычисляет `Transition` через `StageMachine.decide()`
(`fsm.py:51`) — нужно просто `return transition` вместо отбрасывания
результата. `Action.NEXT_STAGE` против `Action.EVALUATE` — ровно нужный
дискриминатор: на `EVALUATE` сессия завершается, открывать нечего.

## Технический нюанс, который определяет форму решения: Anthropic требует непустой список сообщений, начинающийся с роли user

Проверено в `services/ai-service/app/llm/anthropic_provider.py:77-96` —
`messages` передаётся напрямую в `client.messages.create()`. Anthropic
Messages API отклоняет пустой список `messages` или список, не начинающийся
с `role: "user"`. Значит, вызов для открывающей реплики **не может**
отправить пустой список или пустой `user_text`.

Решение: изменений в контракте или в сигнатуре `build_messages()` не
требуется вовсе. Gateway просто передаёт короткую **реплику режиссёра** в
существующее поле `user_text` для открывающих вызовов:
- Начало сессии: `"[Ты говоришь первым — открой разговор по инструкции в системном промпте.]"`
- Переход на этап: `"[Разговор переходит к следующему этапу — продолжи по инструкции в системном промпте.]"`

`build_messages(history, summary, user_text)` в
`services/ai-service/app/character/prompts.py:50-76` уже корректно
обрабатывает это без изменений: для начала сессии `history` пуста, поэтому
результат — единственное валидное сообщение с ролью user; для перехода на
этап `history` заканчивается только что сгенерированной репликой ассистента
(добавлена через `add_turn` внутри первого вызова `_speak` в этом же
`_run_turn`), так что добавление реплики режиссёра как нового сообщения
user сохраняет корректное чередование ролей. **Изменение `build_messages`
не требуется** — это перепроверено против фактической текущей сигнатуры,
а не предположено.

## Изменения промптов — `services/ai-service/app/character/prompts.py`

`_CHARACTER_SYSTEM` (строки 11-27) остаётся без изменений; добавляются
условные блоки. `build_character_system` получает параметры `is_opening:
bool`, `is_session_start: bool`, `off_topic_streak: int`:

```python
_OPENING_SESSION_START = """

ни слова. Поздоровайся и представься в своей роли, затем сразу задай тон
этапа, оттолкнувшись (не дословно!) от ориентира: «{agent_opening}»
Не формулируй прямо или косвенно, что должен ответить собеседник, и не
раскрывай критерий, по которому будет оцениваться этап.

_OPENING_STAGE_TRANSITION = """
Ты уже разговаривал с собеседником — заново не представляйся. Разговор
переходит к следующему этапу. Одной-двумя фразами естественно перейди к

Не формулируй прямо или косвенно, что должен ответить собеседник, и не

_OFF_TOPIC_NUDGE = {
    1: "\n- Последняя реплика собеседника была не по теме этапа. Одной фразой, мягко и в характере, верни разговор в сценарий — не отчитывай.",
    2: "\n- Собеседник уже второй раз подряд уводит разговор в сторону. Твёрдо, но оставаясь в характере, откажись обсуждать постороннее и потребуй вернуться к теме.",

```
`off_topic_streak >= 2` переиспользует уровень 2 (потолок на 2 — см.
«Явные не-цели», `max_turns` остаётся жёсткой страховкой, это только тон).
`stage.completion_criteria` по-прежнему никогда сюда не попадает — разделение
из пункта 4 сохранено.

`CharacterReplyRequest` (`packages/contracts/ath_contracts/api.py:18-25`)
получает два новых поля, оба обратно совместимы:
```python
is_opening: bool = False
off_topic_streak: int = 0
```
Отдельное поле `is_session_start` не обязательно — оно выводимо внутри
`build_character_system` как `is_opening and not history`; либо проще:
gateway сам выбирает, какой из двух открывающих блоков запросить, передавая
`opening_kind: Literal["session_start", "stage_transition"] | None = None`
— это чуть явнее, чем вывод из длины истории на стороне ai-service, и
совпадает с тем, как `Action`/`Classification` уже смоделированы как enum
в остальной части кодовой базы. **Открытый вопрос для реализующего:** любой
из двух вариантов небольшой, выбор не принципиален.

## Стрик ухода от темы — остаётся решением LLM, автомат не трогаем

Добавить `off_topic_streak: int = 0` в `LiveSession`
(`services/gateway/app/orchestrator/session_manager.py:34`, рядом с
`turns_in_stage`). В `TurnPipeline._advance_stage`, сразу после того как
пришла `classification`, до `machine.decide(...)`:
```python
self._session.off_topic_streak = (
    self._session.off_topic_streak + 1
    if classification is Classification.OFF_TOPIC
    else 0
)
```
Эта одна строка уже сбрасывает стрик и на `complete`, и на `incomplete`
(любая классификация, кроме off_topic), а не только при выходе с этапа —
отдельный сброс в `leave_stage()` не нужен, хотя добавить его туда тоже
безвредно, если так читается яснее.

`fsm.py::decide()` не получает **ни нового параметра, ни новой ветки** —
стрик никогда не касается автомата, только промпт следующего `_speak()`.
Это ключевое ограничение из пункта 3 выше.

**Тайминг, явно проверен — задержка не растёт:** `_advance_stage` для хода
N (включая вызов `classify()`) выполняется до конца внутри той же фоновой
задачи, что и `_speak` для хода N, строго до того, как ход N+1 вообще может
начаться (для этого нужно новое событие `UserMessage`, получаемое
последовательно с того же WebSocket, `services/gateway/app/api/ws.py:58-76`).
Единственное исключение — barge-in, отменяющий ход N посреди `_speak`, до
того как `_advance_stage` вообще запустился — тогда ход N просто не
классифицируется, и стрик не трогается, что верно (возвращать не от чего).
То есть классификация предыдущего хода всегда синхронно доступна до того,
как строится промпт следующего — без лишнего обращения к LLM, без
регресса цели ≤1.5 с до первого звука (Claude.md §9).

## Предпосылка: реконнект

Условие `if not session.turns:` для однократного запуска `open_session()`
верно, только если ходы реально восстановлены при реконнекте. Сейчас это
не так: `_restore_session` в `services/gateway/app/api/ws.py:86-108` несёт
собственный TODO (строка 89-90: *«восстанавливать turns и stage_history, а
не только идентификаторы»*) и восстанавливает только `current_stage_id`,
отбрасывая `state.turns`, хотя `SqlSessionRepository.get()` уже возвращает
их полностью (`services/gateway/app/db/repositories.py:47-78`).

Это не редкий крайний случай — `_restore_session` отрабатывает при
**каждом** первом подключении WS к сессии (POST `/sessions` только пишет
строку в БД; `registry.get()` промахивается, пока сокет не подключится ни
разу), поэтому без исправления любая сессия увидит `session.turns == []`
в момент подключения — что верно для действительно свежей сессии, но
настоящий реконнект посреди сценария (перезапуск процесса) тоже увидит
`[]` и ошибочно повторит открывающую реплику. Нужное исправление:
`_restore_session` должен установить `session.turns = state.turns`,
`session.stage_history = state.stage_history` и пересчитать
`session.turns_in_stage` (число ходов с ролью `USER` и `stage_id ==
state.current_stage`). Это входит в объём данной фичи, а не отдельный
follow-up — без исправления открывающая реплика работает неправильно.

## Оптимизация задержки: шаблоны и кэш для открывающей реплики

Момент открывающей реплики особенный: в отличие от реактивного ответа, нет
естественного события «пользователь договорил», которое диктует, когда
генерация ДОЛЖНА начаться — мы сами управляем этим моментом, а значит можем
начать раньше, чем аудио реально понадобится. Три независимые, сочетаемые
оптимизации:

**а) Гибридный шаблон — заранее написанный неизменный текст + короткий
хвост, сгенерированный LLM, вместо генерации всей реплики целиком.**
Самопредставление (имя + роль — «Здравствуйте, меня зовут Ирина, я закупщик
среднего бизнеса.») полностью определяется `persona.name`/`persona.role`,
которые фиксированы для сценария и не требуют вызова LLM вообще:
```python
def build_intro_template(persona: Persona) -> str:
    return f"Здравствуйте, меня зовут {persona.name}, {persona.role}."
```
Эта фраза-шаблон проигрывается первой (сразу ставится в очередь TTS — ноль
задержки LLM для самого первого аудио-чанка), затем следует
сгенерированная LLM фраза-крючок (используя `_OPENING_SESSION_START`/
`_OPENING_STAGE_TRANSITION`) — она короче, потому что ей больше не нужно
заниматься самопредставлением, значит и генерируется быстрее. Это прямой
ответ на «пре-сгенерированный набор фраз, или части, которые используются
на 100%»: представление используется дословно всегда, поэтому оно не
генерируется, а просто форматируется. Для перехода между этапами обычно нет
отдельной фразы-шаблона (представление — только один раз, в начале сессии)
— переход опирается в основном на пункт (в) ниже.

**б) Спекулятивная предгенерация, запущенная как можно раньше:**
- **Начало сессии**: сценарий/персона/первый этап известны в момент
  успешного `POST /sessions` (`services/gateway/app/api/sessions.py`) — ещё
  до подключения WebSocket, и (см. «Экран «Начать тренировку»» ниже) ещё до
  того, как пользователь нажмёт «Начать тренировку». Предложение: запустить
  генерацию открывающей реплики (шаблон + хвост LLM + их TTS) фоновой
  задачей прямо там, закэшированной по `session_id` на стороне gateway, так
  что к моменту, когда клиент реально подключится и разблокирует звук,
  контент уже сгенерирован/синтезирован, и `open_session()` просто
  проигрывает его — превращая ощущаемую задержку первой реплики в
  «сколько времени пользователь читает экран согласия и жмёт кнопку», что
  обычно несколько секунд — с запасом скрывает весь конвейер генерации.
- **Переход между этапами — реальный компромисс, не однозначный выигрыш,
  оставлен как открытый вопрос, а не выбран по умолчанию:** в момент начала
  этапа N мы уже знаем `agent_opening` этапа N+1 (порядок этапов в сценарии
  детерминирован), значит МОЖНО начать генерировать открывающую реплику
  N+1 спекулятивно, пока пользователь ещё на этапе N. Но «учёт контекста»,
  на который опирается открывающий промпт (видит полную историю до момента
  перехода), при ранней генерации работал бы с неполной/предсказанной
  историей — это ослабляет именно то качество, ради которого фича и
  делается. **Рекомендация:** применять оптимизации (а)/(в) и к переходам
  (дёшево, не стоит контекста), но НЕ генерировать хвост перехода
  спекулятивно заранее до фактической классификации `complete` — принять
  живую генерацию здесь, поскольку это второй вызов `_speak`, надстроенный
  над уже выполняющимся ходом (см. «Единый механизм» выше), а не холодный
  старт.

**в) Кэш аудио TTS по ключу `(voice_id, sha256(text))`:** любая реплика с
полностью детерминированным текстом — шаблон представления выше и любая
другая фиксированная «мебель» сценария — никогда не должна попадать в
реальный TTS-провайдер больше одного раза на персону+голос за всё время,
across всех сессий с этой персоной. Небольшой кэш в
`services/speech-service` (для первого прохода достаточно словаря в памяти
процесса — сервис и так один stateless-процесс; потеря кэша при рестарте —
разовая холодная стоимость, не стоит бэкапить в SQLite уже сейчас) по ключу
`(voice_id, sha256(text))` → байты аудио, проверяется в
`services/speech-service/app/tts/*.py` перед вызовом реального провайдера.
Это самая выгодная и наименее рискованная часть здесь — применяется только
к побайтово идентичному тексту, значит не может повлиять на учёт
контекста, и полностью убирает задержку TTS для фразы представления после
первого использования любой персоны кем угодно.

## Экран «Начать тренировку» — фича ломает автоплей браузера, нужен явный жест разблокировки

То, что агент теперь говорит первым (см. выше), убирает жест, на который
сейчас неявно опирается текущий поток: сегодня первое действие
пользователя — набор/отправка сообщения, и этот клик/нажатие клавиши
попутно разрешает последующее воспроизведение аудио с ответом агента по
политике автоплея браузера. Как только агент заговорит ДО любого действия
пользователя, этого неявного жеста больше нет, и `AudioContext.resume()`/
первое воспроизведение молча не дадут звука в Chrome/Safari/Firefox — все
они это применяют. Это жёсткое техническое требование, порождённое именно
этой фичей, а не необязательная полировка — поэтому оно в этом документе,
а не в отдельном follow-up.

**Предлагаемый поток** (`services/frontend/src/pages/TraineeSession.tsx`,
`TalkingHeadAvatar.tsx`):
1. При загрузке страницы показывается экран-оверлей «Начать тренировку»
   (полноэкранный, одна кнопка) вместо немедленного показа интерфейса
   сессии. Существующий `ConsentBanner` (Claude.md §3, §10) естественно
   переезжает на этот же экран — он и так уже момент перед началом
   диалога, и пользователь должен его прочитать до старта в любом случае.
2. За оверлеем, как только известен сценарий (монтирование страницы),
   клиент МОЖЕТ уже открыть WebSocket и дать аудио `open_session()`
   стримиться и буферизоваться на клиенте в `AudioQueue` — создание
   `AudioContext` само по себе не требует жеста, разблокировки требует
   только его ЗАПУСК, так что `head.audioCtx` из `TalkingHeadAvatar` можно
   создать и наполнять данными уже на этом шаге, не нарушая политику. Пока
   ничего не слышно.
3. Клик «Начать» делает две вещи атомарно: (а) реальную разблокировку
   браузера (`audioContext.resume()` / эквивалентный метод инициализации
   TalkingHead) внутри настоящего обработчика клика, что удовлетворяет
   требованию жеста, и (б) показывает интерфейс сессии. Если фоновая
   буферизация из шага 2 уже завершилась (этому помогает предгенерация из
   раздела выше), воспроизведение начинается практически мгновенно; если
   нет — начинается, как только придёт первый чанк, точно как для любого
   обычного ответа.
4. **Рекомендуемый первый проход реализации, проще шага 2:** не открывать
   WS вообще до клика по кнопке; принять обычную задержку `open_session()`
   (смягчённую шаблонами/кэшем выше) после клика. Это по-прежнему корректно
   решает проблему автоплея. Фоновую буферизацию из шага 2 добавить как
   следующий шаг, когда базовый механизм уже проверен и работает.

**Не решается здесь** (вопросы фронтенда/продукта, вне рамок этого
архитектурного документа): точный визуальный дизайн оверлея; отдельный ли
это маршрут или флаг состояния внутри `TraineeSession.tsx` (склоняюсь к
флагу состояния — смена маршрута усложнила бы и без того хрупкий жизненный
цикл подключения/переподключения WS, но выбор за реализующим).

## Явные не-цели

- `fsm.py::decide` — ни новой ветки, ни нового параметра. Уход от темы
  остаётся полностью в ведении промпта, по уже существующему принципу
  кодовой базы.
- Порядок `_speak`-затем-`_advance_stage` для обычных ходов не меняется —
  задержка реактивных ответов не растёт. Открывающий вызов `_speak` для
  нового этапа — это ВТОРОЙ, отдельный проход LLM+TTS, добавленный ПОСЛЕ
  `_advance_stage`, под тем же `gen_id` — неизбежно, поскольку это новый
  контент, а не переупорядочивание существующей работы.
- `stage.max_turns` (уже применяется в `fsm.py:75-82`) остаётся
  единственной жёсткой страховкой от бесконечного застревания на уходах от
  темы. Уровни тона по стрику — это только тон, они намеренно перестают
  усиливаться на стрике 2, а не изобретают ещё один механизм
  принудительного перехода.
- Никакой Redis/постоянной инфраструктуры кэша — кэш TTS из раздела выше
  живёт в памяти процесса, что соответствует уже существующей позиции
  проекта «один воркер, Redis — когда реально понадобится»
  (`docs/architecture.md`).

## Граничные случаи и открытые вопросы

- **Barge-in во время открывающей реплики**: работает без специальных
  случаев — и `open_session()`, и открывающий вызов при переходе
  регистрируются в `generations` точно как обычные ходы, поэтому
  `UserMessage{interrupts}` отменяет их одинаково.
- **Сессия брошена посреди генерации открывающей реплики**: покрыто
  существующим `finally: await session.generations.cancel_all()` в
  `ws.py`; `_speak` сохраняет ход только после того, как стрим полностью
  завершится, поэтому отменённая открывающая реплика никогда не оставляет
  частичную запись в БД.
- **Открывающая реплика идёт через обычный конвейер TTS/сплиттера**: да,
  без изменений — `_speak(is_opening=True)` по-прежнему запускает
  `SentenceSplitter`, `_synthesize`, отправляет `TokenEvent`/
  `AudioChunkEvent`/`SubtitleEvent` точно как любой ответ. Никакого обхода,
  никакого нового типа события WS.
- **Подписи спанов в админ-панели** (`_speak`, pipeline.py:174-176):
  текущая подпись `f'{persona_name}: ответ на "{user_text[:60]}"'` покажет
  реплику режиссёра в квадратных скобках для открывающих спанов — путает в
  `/admin/sessions/<id>`. Использовать отдельную подпись вроде
  `f'{persona_name}: открывает этап "{stage.id}"'` при `is_opening=True`.
  Мелкая полировка, но стоит упомянуть — админ/Gantt-панель уже существует.
- **Открытый вопрос — сбой LLM во время открывающего вызова**: неудачный
  обычный ответ посреди сценария хотя бы происходит после того, как
  пользователь уже что-то сказал; неудачный вызов ИМЕННО открывающей
  реплики оставляет пользователя в тишине без повода отреагировать. Нужен
  ли резервный вариант без LLM, отправляющий `stage.agent_opening`
  дословно как последнее средство, именно для `open_session()` при ошибке?
  Это компромисс между «никогда не произносить дословно» и «никогда не
  оставлять пользователя в полной тишине» — отмечено, не решено.
- **Открытый вопрос — спекулятивная предгенерация перехода между этапами**
  (раздел выше, пункт б): оставлен как задокументированный компромисс, а
  не выбор по умолчанию; вернуться к вопросу после того, как появятся
  реальные цифры задержки от оптимизации начала сессии.

Живая приёмка на Docker с реальными провайдерами (Anthropic + Soniox),
скрипты — в скретчпаде сессии:

1. Подключиться к свежей сессии и **ничего не отправлять**. Ожидание:
   `token`/`audio_chunk` приходят сами. Получено: реплика приходит, первый
   звук — 94-125 мс.
2. Продавить `max_turns`, чтобы этап сменился принудительно. Ожидание:
   `action=next_stage`, а следом — реплика, которой никто не запрашивал,
   с тем же `gen_id`. Получено: подтверждено.
3. Переподключиться к той же сессии. Ожидание: тишина, приветствие не
   повторяется. Получено: подтверждено.
4. Дважды подряд ответить не по теме. Ожидание: второй ответ заметно
   твёрже. Получено: «давайте ближе к делу» → «либо говорите, зачем
   звоните, либо я кладу трубку».

## Результаты прогона: что живой запуск изменил в этом документе

Три правки, которых не было в исходном плане, — все три нашлись только на
реальных провайдерах:

- **Двойное приветствие.** Шаблон представления здоровается, а `agent_opening`
  в сценарии сам начинается с «Здравствуйте» — модель шла за ориентиром и
  здоровалась второй раз подряд. Промпт открытия теперь показывает модели
  уже сказанную фразу и прямо запрещает здороваться повторно.
- **Ремарки в скобках.** Модель выдала «(разговор завершён)Ладно, слушаю…» —
  TTS произнёс бы это вслух. Правило про разметку такого не покрывало;
  добавлено отдельное, про прямую речь без описаний действий.
- **`log.debug(..., event=...)` роняло отброс устаревшего чанка.** У structlog
  `event` — это само сообщение, поэтому одноимённый kwarg давал `TypeError`
  вместо тихого игнорирования. Баг был не новый, но лежал ровно на пути
  метрики 4 и срабатывал только при реальном отбросе; закрыт тестом
  `test_stale_event_is_dropped_quietly` (он падает без исправления).

Открытый вопрос про запасной путь при сбое LLM (ниже, «Граничные случаи»)
решён в пользу запасного пути: `_speak_fallback_opening` озвучивает
`stage.agent_opening` дословно. Причина — альтернатива не «чуть хуже
сформулировано», а тишина в начале сессии, когда сотруднику не на что
реагировать. Убрать его — один `except`-блок в `_run_opening`.

Спекулятивная предгенерация при `POST /sessions` (раздел «Оптимизация
задержки», пункт б) **не реализована**: кэш TTS и шаблон представления уже
дали 94-125 мс до первого звука, и усложнять ради оставшегося запаса
незачем, пока цифры такие.
