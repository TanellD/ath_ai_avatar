# Хранение данных

Что физически лежит на диске, где именно, и чего в архитектуре сознательно
или несознательно ещё нет. Дополняет [architecture.md](architecture.md)
(поток одного хода) и [contracts.md](contracts.md) (форма данных на
проводе) — здесь про то, что переживает процесс.

## Обзор

| Хранилище | Владелец | Формат | Что содержит |
|---|---|---|---|
| `data/gateway.db` | `gateway` | SQLite (WAL) | сессии, ходы, спаны конвейера, отчёты |
| `data/scenarios.db` | `scenario-service` | SQLite (WAL) | сценарии (шаблоны и копии методиста) |
| — | `ai-service` | нет | stateless: запрос → ответ, ничего не пишет на диск |
| — | `speech-service` | нет | stateless: то же самое |
| браузер, `localStorage`/память | `frontend` | — | ничего не персистится дольше вкладки (кроме черновика правок сценария в памяти компонента) |

Оба SQLite-файла смонтированы в контейнеры через `./data:/data`
(`docker-compose.yml`) — то есть переживают `docker compose down`, но не
переживают удаление хост-папки. Комментарий в `data/.gitkeep` — единственное,
что попадает в git; сами `.db`/`.db-shm`/`.db-wal` в `.gitignore`.

Postgres — закомментированный сервис в `docker-compose.yml`, на будущее.
Переезд не требует правок в моделях или репозиториях: единственная
SQLite-специфика (`PRAGMA journal_mode=WAL` и т.п.) обёрнута в
`app/db/engine.py::_sqlite_pragmas` и просто не сработает на другом диалекте.

## `gateway.db`

Схема — `services/gateway/app/db/models.py`.

### `users`

Владелец артефактов — **не авторизация** (Claude.md §4 её явно исключает).
Ровно две строки, засеянные при старте (`app/db/seed.py::seed_default_users`,
вызывается из `lifespan()` после `init_engine()`), с фиксированными id
`employee-1`/`methodist-1`:

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | `String(64)` PK | `employee-1` \| `methodist-1` — константы, не генерируются |
| `role` | `String(16)` | `employee \| methodist` |
| `display_name` | `String(128)` | «Сотрудник» / «Методист» — то, что видно в админ-панели |

Когда понадобится больше одного сотрудника/методиста — таблица уже на
месте, добавлять нечего: убрать засев фиксированных id, завести реальное
создание пользователей и (отдельно) решить вопрос аутентификации, который
Claude.md сознательно выводит из скоупа кейса.

### `sessions`

Одна строка на тренировочную сессию.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | `String(36)` PK | `session_id`, UUID |
| `scenario_id` | `String(128)` | ссылка на сценарий (в другой БД — без FK, сервисы независимы) |
| `user_id` | `String(64)`, FK → `users.id` | кто проходит тренировку. Внутренняя деталь, не часть `ath_contracts.SessionState` (§7) — как и `gen_id` у `turns`; сегодня всегда `employee-1`, задел на будущее |
| `current_stage` | `String(128)` | id текущего этапа FSM |
| `current_gen` | `Integer` | последнее известное поколение (дублирует `GenerationRegistry` в памяти — на случай рестарта) |
| `status` | `String(16)` | `active \| finished \| abandoned` |
| `stage_history` | `JSON` | список `StageHistoryEntry` — какие этапы пройдены, за сколько ходов, почему вышли |
| `summary` | `Text` | сжатая выжимка старых ходов для окна контекста (§5) |
| `created_at` / `finished_at` | `DateTime` | `created_at` — `server_default=func.now()`; `finished_at` пишется при завершении |

### `turns`

Одна строка на реплику — и сотрудника, и персонажа.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | PK autoincrement | суррогатный ключ |
| `session_id` | FK → `sessions.id`, `ON DELETE CASCADE` | |
| `index` | `Integer` | порядковый номер в сессии; уникален вместе с `session_id` (`ix_turns_session_index`) |
| `role` | `String(8)` | `user \| agent` |
| `text` | `Text` | текст реплики. Для сотрудника в голосовой фазе — выход STT, не истина (см. `stt-phase.md`) |
| `stage_id` | `String(128)` | этап, на котором произошёл ход |
| `ts` | `Float` | секунды от начала сессии |
| `stt_confidence` | `Float \| null` | `[STT]` заполняется только с голосом |
| `audio_ref` | `String(512) \| null` | `[STT]` заполняется только с голосом — указатель на аудио-сегмент, см. «Чего пока нет» ниже |
| `gen_id` | `Integer` | поколение, в рамках которого возник ход. Внутренняя деталь, **не** часть `ath_contracts.Turn` (§7) — наружу в продуктовый контракт не идёт, нужна только чтобы сгруппировать ход с его спанами для админ-панели |

Пишется дважды за ход: реплика сотрудника — сразу при получении
(`fire-and-forget`, чтобы не задерживать обработку следующего события и не
есть бюджет barge-in), реплика персонажа — по окончании стрима, за пределами
критического пути ответа.

### `spans`

Один шаг конвейера одного хода — данные Gantt-графика в админ-панели
(`services/gateway/app/tracing.py`, `app/api/admin.py`). См. «Архитектура
событий» ниже — это единственный существующий event-лог в проекте, и он
узкоспециализирован.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | PK autoincrement | |
| `session_id` | FK → `sessions.id`, `ON DELETE CASCADE` | |
| `gen_id` | `Integer` | какой ход |
| `seq` | `Integer` | порядок операций внутри хода (0, 1, 2, …) |
| `operation` | `String(64)` | `character_reply \| tts_synthesize \| classify` |
| `label` | `Text` | что именно — префикс реплики персонажа / текст предложения TTS / этап классификации |
| `start_ms` / `end_ms` | `Integer` | относительно начала **этого хода**, не сессии |
| `status` | `String(16)` | `ok \| error \| cancelled` |
| `error` | `Text \| null` | первые 500 символов исключения, если `status = error` |
| `created_at` | `DateTime`, `server_default=func.now()` | настенное время записи — единственная абсолютная временная метка в этой таблице (`start_ms`/`end_ms` относительны началу хода). Нужна только для графика активности во времени в `/admin/load` |

Пишется по завершении каждой операции сразу (не батчем в конце хода) — если
ход отменят на середине (barge-in) или упадёт с ошибкой, спан всё равно
попадёт в таблицу. Запись — best-effort: исключение при записи спана
логируется и глушится, ход пользователю от этого не пострадает
(`SpanRecorder._persist`).

`character_reply` намеренно охватывает весь стрим токенов целиком, включая
вложенные `tts_synthesize` — конвейер сейчас последовательный (не
распараллелен), и это честно отражает реальное перекрытие по времени, а не
пытается выделить «чистое время LLM».

### `reports`

Один-к-одному с `sessions` (PK = `session_id`).

| Колонка | Тип | Смысл |
|---|---|---|
| `session_id` | `String(36)` PK, FK → `sessions.id` | |
| `verdict` | `Text` | текстовый вывод |
| `total_score` | `Float` | |
| `payload` | `JSON` | весь `Report` (§7) целиком, как отдан клиенту — источник истины для `evidence`/`audio_ref` под каждым баллом |
| `created_at` | `DateTime` | |

`payload` дублирует `verdict`/`total_score` — это осознанно: колонки нужны
для будущей выборки списком без разбора JSON (как в `scenarios.stages_count`
ниже), `payload` — потому что перечитывать `Report` для отдачи клиенту
нужно целиком и как есть.

## `scenarios.db`

Схема — `services/scenario-service/app/db/models.py`. Одна таблица,
`scenarios`: `id` (PK), `title`, `persona_name`, `stages_count`,
`rubric_count`, `is_template`, `payload` (весь `Scenario` из §7 целиком),
`created_at`/`updated_at`. Сценарий хранится одним JSON-документом
сознательно — он всегда читается/пишется целиком, а нормализация по
persona/stages/rubric дала бы миграцию на каждое изменение формы и не дала
бы ничего взамен (в постановке нет запросов вида «сценарии с difficulty > 3»).

## Что не персистится

WebSocket-события (`token`, `audio_chunk`, `subtitle`, `action`, `cancel`,
`transcript`) — целиком транзитные. Они существуют только на проводе между
`gateway` и браузером на момент отправки; ни один из них не пишется на
диск как отдельная строка. То, что от них остаётся:

- `token` → финальный склеенный текст попадает в `turns.text` (не сами токены)
- `audio_chunk` → длительность попадает в `subtitle.start_ms/end_ms`, но
  сами аудио-байты **нигде не сохраняются** — ни в текстовой фазе (звук
  синтетический, воспроизводится и выбрасывается), ни пока в голосовой
- `subtitle` → не персистится вообще, чисто клиентский рендер
- `action`/`cancel` → эффект виден в `sessions.current_stage`/`stage_history`
  и в `spans.status = cancelled`, сами события — нет

## Чего в архитектуре пока нет (осознанные пробелы)

**Аудио-сегменты сотрудника.** Claude.md §7/§10 требуют хранить короткие
(≈5 с) фрагменты аудио под `audio_ref` в отчёте — это то, что делает цитату
`evidence` проверяемой за десять секунд при возможной ошибке STT. Колонка
`turns.audio_ref` заведена заранее (см. таблицу выше), но ничего в неё не
пишет: текстовая фаза не производит аудио сотрудника, писать некуда.
Реализация — задача голосовой фазы (`docs/engineering/stt-phase.md`): нужны место
хранения (файлы на томе рядом с `.db`, или BLOB-колонка — решить при
реализации), формат `audio_ref` (сейчас просто `String(512)`, по
контракту `AudioRef = {turn, start_ms, end_ms}` — что это, путь или URL,
не зафиксировано) и retention (`AUDIO_RETENTION_DAYS`, упомянут как план в
`ConsentBanner.tsx`, нигде не реализован).

**Метрики приёмки (§9).** Time to first audio, время остановки при
перебивании, число возвратов отменённого хвоста — ни одна из шести метрик
приёмки нигде не считается и не сохраняется. `spans` даёт сырой материал,
из которого TTFA и латентность отмены можно было бы вывести (например,
TTFA ≈ `start_ms` первого `tts_synthesize`-спана; возврат отменённого
хвоста проверяется тем, что после `cancelled`-спана для `gen_id` не
появляется новых событий с тем же `gen_id`), но сегодня это нужно
вычислять вручную запросом к БД — нет ни таблицы под агрегаты, ни job,
который бы их считал на лету.

**Стоимость.** §9, метрика 6 требует «себестоимость минуты, ≤ 10 ₽» —
посчитана. Ни `ai-service`, ни `speech-service` не читают и не
прокидывают наверх usage-поля своих провайдеров (токены у Anthropic,
символы/минуты у Soniox) — `services/ai-service/app/llm/*.py` не трогает
`response.usage` вообще. Посчитать стоимость сессии сегодня нечем, кроме
как оценкой по логам провайдера снаружи системы.

## Архитектура событий для аналитики — что есть и чего не хватает

Сегодня в проекте фактически два разных, никак не связанных слоя данных:

1. **Продуктовый слой** (`sessions`, `turns`, `reports`) — то, что видит
   методист. Устойчивый, по контракту §7, меняется редко.
2. **Отладочный слой** (`spans`) — внутренний инструмент понимания
   конвейера (админ-панель, Gantt), сознательно вынесенный из
   `ath_contracts` (`app/db/admin_repository.py`, шапка файла: «не
   продуктовый контракт»). Это, по сути, единственный event-лог в системе:
   типизированная последовательность операций с таймингами и статусом.

`spans` устроен как append-only лог с полями `(session_id, gen_id, seq,
operation, label, start_ms, end_ms, status, error)` — это уже форма,
из которой растут нормальные analytics-события, но назначение узкое:
операции **внутри одного хода**, для отладки задержки. У него нет:

- уровня события выше хода — нет строки «сессия началась»/«сессия
  завершена»/«методист открыл отчёт»;
  session-level факты сегодня выводятся из `sessions.status` +
  `finished_at`, а не из событий;
- типизированного `payload` для метрик — `label` это текст, не число;
  чтобы посчитать TTFA или стоимость, каждый раз нужен ad hoc разбор;
- ретеншна/агрегации — таблица растёт бесконечно, ничего её не сворачивает
  в дневные/сессионные агрегаты.

**Если аналитика (не отладка одного хода, а «сколько сессий в день»,
«средняя себестоимость», «где чаще всего проваливается TTFA») понадобится
всерьёз, дешевле не городить отдельную event-платформу, а:**

1. Добавить в `SpanRecorder`/`_run_turn` два-три новых типа операций уже в
   существующую таблицу `spans` — `llm_first_token`, `tts_first_chunk`,
   `barge_in_stop` — они бесплатно попадают в тот же Gantt и в ту же
   таблицу, никакой новой инфраструктуры.
2. Завести **одну** новую таблицу `session_metrics` (session_id PK,
   пригоршня числовых колонок: `ttfa_ms`, `stale_returns`, `llm_tokens_in`,
   `llm_tokens_out`, `tts_chars`, `cost_rub`) и заполнять её одним UPDATE
   при завершении сессии — не событийный поток, а посчитанный снапшот.
   Это ровно то, что нужно для отчёта по метрикам §9, без обязательства
   поддерживать общую event-шину.
3. Не делать общий `events`-стол на все случаи жизни заранее — в проекте
   этого масштаба (кейс, не прод с реальной нагрузкой) он либо не
   заполнится реальными типами событий, либо будет John Do нормализацией
   ради нормализации, которую и так уже один раз сознательно отвергли для
   `scenarios.payload`.

Короче: инфраструктура для аналитики де-факто уже начата (`spans` —
это MVP event-лога), просто её область — один ход, а не вся сессия и не
себестоимость. Расширять стоит вглубь той же таблицы + один агрегатный
снапшот, а не вширь новой подсистемой.

### Что из этого уже сделано

Пункт 1 (`GET /admin/load`, `app/db/admin_repository.py::get_load_stats`)
реализован — но не как отдельная таблица-снапшот (пункт 2 выше), а как
агрегат по `spans` на лету: группировка по `operation`, count/avg/p95 по
`end_ms - start_ms`, ошибки/отмены по `status`. Для текущего объёма данных
(кейс, не прод-нагрузка) считать при каждом запросе дешевле, чем
поддерживать отдельную таблицу и код инвалидации для неё — тот самый
принцип «не городить лишнего», просто применённый ещё раз. p95 считается в
Python (`_percentile`), а не оконной функцией SQL: датасет мал, а
завязываться на диалект-специфичный SQL ради процентиля здесь не нужно.

Таймлайны (`sessions_timeline`/`activity_timeline`) сначала были посуточными
(`func.date(sessions.created_at)`), но дневная гранулярность для этого
проекта бессмысленна — тестовые сессии идут пачками за минуты в рамках
одного дня, и график состоял из одного столбика. Заменены на бакеты по 30
секунд (`_timeline()`) за скользящее окно (по умолчанию последние 30 минут),
с подписью `HH:MM:SS`, посчитанные так же в Python и по тем же причинам, что
и p95. Ради этого у `spans` появилась `created_at` (см. таблицу выше) —
`start_ms`/`end_ms` относительны началу хода и не годятся для оси
абсолютного времени.

`ttfa_ms`/`cost_rub`/`llm_tokens_*` из пункта 2 всё ещё не собираются —
это по-прежнему открытый пробел (см. «Метрики приёмки» и «Стоимость»
выше); `get_load_stats` даёт нагрузку и латентность по операциям, но не
считает деньги.

### Оффлайн-инструмент: `scripts/session_gantt.py`

Веб-версия Gantt-графика в `/admin/sessions/<id>` рисует один ход за раз.
Для разбора сессии целиком — сколько сообщений было, где потрачено время
на каждом, где конвейер параллелится (пока не параллелится нигде, кроме
логического наложения `tts_synthesize` внутри `character_reply` — см.
`docs/engineering/architecture.md`) — есть отдельный офлайн-скрипт: тянет `/admin/sessions/<id>/gens`
и `.../spans` через голый `urllib`, рисует все ходы сессии друг под другом
в один PNG через `matplotlib` (`pip install -r scripts/requirements.txt`).
Каждый спан — один горизонтальный бар на своей строке; если в будущем
появится реальный параллелизм (TODO в `pipeline.py::_speak`), он проявится
как перекрытие баров по оси времени — тот же принцип, что и в
`GanttChart.tsx`, просто без браузера и без gateway, поднятого локально
через `--api-url`.

## Известный операционный риск: нет миграций

`app/db/engine.py::init_engine` поднимает схему через
`Base.metadata.create_all` при каждом старте — это создаёт отсутствующие
таблицы, но **не** меняет существующие. Это не гипотетический риск: при
добавлении `spans` и колонки `turns.gen_id` (админ-панель, эта же
итерация) `create_all` создал новую таблицу `spans` в уже существующей
`gateway.db`, но не добавил `gen_id` в уже существующую `turns` — пришлось
руками накатывать `ALTER TABLE turns ADD COLUMN gen_id …` на файл в
`data/gateway.db`, иначе старые локальные БД (в том числе у любого, кто
клонирует репозиторий поверх уже накопленных данных) не поднялись бы.
Alembic заведён как TODO (`app/alembic/README.md`) и не подключён —
до первой реальной ревизии это единственный путь эволюции схемы.

Повторилось один в один при добавлении `users` и `sessions.user_id` в этой
же итерации: `create_all` создал `users` (новая таблица), но не добавил
`user_id` в уже существующую `sessions` — снова понадобился ручной
`ALTER TABLE sessions ADD COLUMN user_id … DEFAULT 'employee-1'`. Плюс к
этому дежурная ловушка dev-режима: `docker-compose.override.yml`
поднимает gateway с `--reload` на bind-mount исходников, и реcтарт
воркера по изменению файла **не** переоткрывает уже установленные
SQLAlchemy-соединения к БД — после ручного `ALTER TABLE` из другого
