# ADR 0001. STT: модель, runtime, границы и watchdog'и

Статус: принято, часть значений помечена как дев-умолчания до замеров.
Контекст: [`../voice-input-plan.md`](../voice-input-plan.md), фазы 0–3.

Этот документ фиксирует, что именно прибито в коде и почему. Значения, которые
план разрешает менять только по результатам собственного бенчмарка, помечены
**[ждёт замера]** — они сознательно консервативны и не выдают себя за
измеренные.

## 1. Канонический формат аудио

`PCM signed 16-bit little-endian, 16 kHz, моно` — один формат от AudioWorklet
до обоих движков.

Ресемплинг делает только браузер. Gateway и speech-service считают сэмплы, но
не пересчитывают их: второй ресемплинг в середине пути — это лишняя потеря
качества и второй источник расхождения таймингов. Тайминги считаются как
`total_samples / 16000`, а не по настенным часам.

## 2. Локальный движок

| Решение | Значение | Почему |
|---|---|---|
| Модель | `v3_e2e_ctc` | 220M-класс, как требует план; e2e-вариант даёт пунктуацию без отдельной модели |
| Runtime | PyTorch CPU | ONNX **[ждёт замера]**: без цифр переход не обоснован |
| Сборка | `torch==2.10.0+cpu`, `torchaudio==2.10.0+cpu` | явный CPU-индекс, иначе pip тянет CUDA-runtime в образ |
| Устройство | `cpu` | демо-машина без GPU |
| Параллелизм | 1 инференс + очередь 1 | CPU-инференс не масштабируется потоками; перегруз обязан отвечать 429, а не копить латентность |
| Число CPU-потоков | не задано **[ждёт замера]** | по умолчанию torch берёт все ядра; ограничивать без замера RTF нет оснований |

600M-модель запрещена без доказанной выгоды по замеру — так требует план.

### Целостность весов

`services/gigaam-worker/models.lock.json` пинит sha256 обоих артефактов и md5
чекпоинта. md5 совпадает с `_MODEL_HASHES` в официальном `gigaam/__init__.py` —
это то же значение, которое библиотека ассертит в `load_model`. sha256 наш и
покрывает ещё и токенизатор, для которого upstream не публикует ничего.

Штатный старт офлайновый: worker проверяет комплектность кеша и падает в
`/ready` с указанием на `make gigaam-setup`. Иначе `gigaam.load_model` молча
ушёл бы качать ~450 МБ с CDN во время демо, и единственным симптомом был бы
бесконечный `/ready`.

## 3. Soniox

| Решение | Значение |
|---|---|
| Модель | `stt-rt-v5` |
| Эндпоинт | `wss://stt-rt.soniox.com/transcribe-websocket` |
| Формат | `pcm_s16le`, 16000, 1 канал |
| Соединение | одно на capture, не постоянное |

Соединение на ход, а не постоянный поток: пауза в постоянном потоке всё равно
требует keepalive и тарифицируется по полной длительности. Выбор между
постоянным соединением и посессионным — вопрос латентности против стоимости и
пересматривается **[ждёт замера]**, а не по умолчанию.

## 4. Watchdog'и и границы

| Параметр | Значение | Обоснование |
|---|---|---|
| `STT_FINALIZE_TIMEOUT_SECONDS` | 5 с | нормальный final измерен около 320 мс; 5 с — консервативный дев-порог, чтобы не переключаться на шуме **[ждёт замера p95]** |
| `GIGAAM_TIMEOUT_SECONDS` | 60 с | верхняя граница HTTP-запроса к worker'у; не продуктовое значение **[ждёт замера RTF]** |
| `VOICE_MAX_CAPTURE_SECONDS` | 20 с | дев-страховка; GigaAM short-form начинает деградировать после 25 с. 20 с = 640 000 байт (~625 KiB) |
| `VOICE_MAX_FRAME_BYTES` | 32 000 | один кадр не должен позволять обойти лимит длительности |
| `GIGAAM_QUEUE_SIZE` | 1 | одна ожидающая задача; дальше 429 |
| healthcheck `start_period` | 180 с | веса скачаны заранее, остаётся только загрузка чекпоинта с тома |

## 5. Failover

Одно переключение за ход: `Soniox → GigaAM`, обратно внутри хода — никогда.
Для GigaAM повторного fallback нет: падать некуда, и цепочка попыток только
затянула бы потерянный ход.

Триггеры переключения: провал `open`, ошибка `push`, ошибка `finalize`,
`ProviderFault`, обрыв потока и молчание после `finalize` дольше watchdog'а.
Обрыв сокета сам по себе триггером не является — им является отсутствие
прогресса.

`provider_epoch` растёт на единицу и только на единицу. Gateway принимает
только `N+1`; всё, что меньше текущего, отбрасывается как опоздавшее, всё, что
больше, — как невозможное. Восстановление Soniox происходит на следующем
capture: `create_stt_provider` вызывается на каждое WS-соединение, поэтому
деградация предыдущего хода не переносится на следующий.

Клиенту сообщается не сбой, а следствие: `voice_provider_switched` с
`partials_available`. Имя движка в UI не показывается.

## 6. Политика здоровья и восстановления

Отдельного health-цикла у провайдеров нет намеренно. Здоровье проверяется тем
же ходом, который его использует: неудача переключает, следующий ход пробует
основной движок заново. Отдельный пробник добавил бы третий источник правды о
состоянии Soniox и собственные ложные срабатывания.

## 7. Что ещё не измерено

Ни одно из значений ниже не должно попасть в продакшн-профиль без цифр:

- RTF, cold/warm latency, RSS и качество GigaAM на нашем корпусе;
- WER, критические сущности и потерянные отрицания против Soniox;
- p50/p95 для `first_partial`, `finalization`, `response_ttfa`;
- матрица браузеров и устройств шире desktop Chrome;
- пороги качества корпуса и продуктовая максимальная длительность хода.

Инструмент для первых двух пунктов готов: `benchmarks/stt/run_gigaam.py` и
`benchmarks/stt/scoring.py`. Не хватает самих записей — их нельзя ни
сгенерировать, ни позаимствовать: нужен свой корпус с согласием говорящих.
